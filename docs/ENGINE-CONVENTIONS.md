# Writing engine code (`src/OniBrutal.UnityEngine`)

Rules for every hand-written file in the engine assembly. The why is in `ARCHITECTURE.md`.

## Shape comes from Unity, bodies come from us

- `Generated/` holds the **shape** of every Unity type the game needs: enums (with values),
  interfaces, delegates, and *type headers* (modifiers, base type, interfaces, generic
  constraints, `[Serializable]`, `[AttributeUsage]`, `[RequireComponent]`…, abstract members).
  It is produced by `scripts/regen-surface.sh` (tools/SurfaceGen). Never edit it.
- Hand-written code adds members in **partial** declarations: `public partial class Camera`
  (no base list, no modifiers besides accessibility). For Unity types that are *internal*, write
  `partial class X` with no accessibility modifier.
- Never declare a public type that Unity doesn't have: FacadeGen fails the build. Engine
  internals go in namespace `OniBrutal.Engine` (or nested `OniBrutal.*`) and are `internal`.

## Which members exist

- The members consumers reference are listed in `out/surface/members.txt` (generated by
  `tools/Inventory`; rows are `Type<TAB>signature<TAB>consumers`). `tools/ApiCheck` is the gate.
- A member is implemented **completely or not at all**. No `throw new NotImplementedException()`,
  no silent no-ops, no "TODO: real logic". If Unity's behaviour for a member cannot be
  reproduced faithfully yet, leave the member out; the runtime then fails loudly with
  `MissingMethodException` if anything ever calls it.
- Where Unity's own behaviour *is* a no-op (editor-only APIs in a player, `Gizmos`, …), implement
  it as that no-op with a one-line comment saying why.
- Members unreferenced by consumers may be added when they are part of a coherent type (e.g. the
  standard operators of a math struct) and their Unity behaviour is known exactly.

## Unity semantics

- Signatures must match Unity's exactly (name, parameter types, static/instance, return type,
  `virtual`/`override`/`sealed`), because game IL binds by signature. Parameter names should
  match Unity's too (named arguments, reflection).
- Unity's API has no nullability annotations; the project has `<Nullable>disable</Nullable>`.
- Behaviour follows Unity's documented and observable behaviour. Comment non-obvious rules
  (e.g. "inclusive at min, exclusive at max").
- **No managed reference fields on `UnityEngine.Object` subclasses** except what Unity itself
  declares there. Engine state for objects lives on the "native side" (`OniBrutal.Engine`
  records reached through `Object.m_CachedPtr`). Game code reflects over component fields.
- Value types keep Unity's exact public fields (KSerialization reflects over them).
- Threading: see ARCHITECTURE §4. Main-thread-only APIs call `OniBrutal.Engine.Threads.AssertMainThread(name)`.

## Style

- File per type or per small family, under a folder named for the Unity area
  (`Math/`, `Core/`, `Rendering/`, `UI/`, `UIElements/`, `Playables/`, `TextCore/`, …).
- Comments state Unity rules and reasons, not narration.
- `TreatWarningsAsErrors` is on.
